# Custom SAPI

A standalone PHP SAPI based on the project generated by `tools/phpz_skel.php`.
It runs a PHP script file or code passed with `-r` and provides one built-in function,
`custom_sapi_greeting(): string`.

- `src/main.zig`: custom function, module entry, SAPI callbacks and PHP lifecycle.
- `custom_sapi.stub.php`: PHP API declarations.
- `custom_sapi_arginfo.h`: generated arginfo.
- `tests/`: PHP scripts that verify the executable.

## Initialization

Define the built-in module and SAPI callbacks:

```zig
var app_module = phpz.initModuleEntry(.{ .name = "custom_sapi_app" });

const Sapi = phpz.sapi.Sapi(Backend, .{
    .name = "custom_sapi",
    .ub_write = Backend.write,
});
```

`initModuleEntry()` returns caller-owned storage without exporting a PHP loader
entry point. Keep it alive through PHP module shutdown. Use `phpz.module()` when
building an extension that PHP loads separately.

After initializing TSRM and Zend signals, create a local instance:

```zig
var sapi = Sapi.init(.{
    .ini_ignore = true,
    .ini_ignore_cwd = true,
    .info_format = .text,
    .ini_entries = "display_errors=0\nlog_errors=1\n",
});
try sapi.startup(&app_module);
```

`init()` initializes SAPI state. `startup(addon)` then starts the PHP engine and
its modules. Select the built-in module at runtime, or pass `null` for none;
it cannot be switched after startup. Start and shut down each request with
`phpz.sapi.request.startup()` and `shutdown()`. After all requests and worker
threads finish, call `sapi.shutdown()`, `sapi.deinit()`, then shut down TSRM.
Only call `sapi.shutdown()` after a successful `startup(addon)`.

Request startup failure does not roll back partially activated PHP state. Treat
it as terminal for the host: shut down PHP modules, SAPI and TSRM, then release
borrowed backend resources and exit. Do not retry or serve another request with that runtime.
The example propagates the error out of `main`; its host defers perform teardown.
Only install the normal request-shutdown defer after request startup succeeds.

The instance owns its module table; PHP supports one active SAPI per process.
Keep the instance and borrowed INI text alive through shutdown. Use
`sapi.ptr()` for additional configuration before `startup(addon)`; do not move the
instance while holding that borrowed pointer.

Perform application-specific initialization and cleanup around
`sapi.startup(addon)` and `sapi.shutdown()` in the host program.

See `src/main.zig` for the complete lifecycle.

To execute code text during an active request, use
`try phpz.tryEval("echo custom_sapi_greeting();", null, "Custom SAPI code")`.
Omit the `<?php` tag. Output uses the current SAPI callbacks; the last argument
identifies the code in diagnostics. This does not apply prepend/append files.
Pass a `*Zval` instead of `null` to evaluate an expression: PHP wraps the code as
`return <code>;`. Initialize the output slot to undef and release the result
before request shutdown; existing slot contents are not released.
PHP exceptions return `error.PhpException` and remain pending. Inspect them with
`phpz.errors.exception()`; preserve them when propagating to PHP, or call
`phpz.errors.clearException()` after handling them. `tryEval` catches PHP bailouts
and returns `error.ZendBailout`; after a bailout, proceed to request shutdown rather
than continuing PHP execution. The lower-level `eval` propagates bailouts.
Exception reporting needs its own `phpz.zend.bailout.run` boundary because it can
execute PHP code. Keep request shutdown and mandatory host cleanup outside these
boundaries: a bailout skips Zig defers inside it. See `src/main.zig` for both paths.

For a script file, use `phpz.tryExecuteScript(file)` with a `zend.FileHandle`.
PHP reports script exceptions and maps its internally caught failures to
`error.ScriptExecutionFailed`; the outer boundary catches escaping bailouts as
`error.ZendBailout`. The caller still owns the handle and request lifecycle.
The lower-level `executeScript` delegates directly to PHP's script runner.

Bind the request backend with `Sapi.setContext(&backend)` after PHP module startup
and before request startup. Keep it bound through request shutdown, then clear it
with `Sapi.setContext(null)`. Without a backend, request callbacks are skipped
and `ub_write` returns zero without writing. Fallback logs use `std.log.err`.

For HTTP backends, prepare body and cookie state before request startup: PHP may
read them before `activate`. A `read_post` callback must fill the supplied buffer
unless the request body ends; PHP treats any short read as EOF. Handle transport
short reads within the callback and never consume bytes from the next request.

`ub_write` must write all bytes or return an error. Errors from `ub_write` and
`flush` mark the connection aborted, with termination controlled by
`ignore_user_abort`. Errors from `deactivate` are logged only. This callback is a
notification, not a guaranteed destructor: a bailout while PHP drains the remaining
request body can skip it, and failed request startup does not guarantee a call.
Use host-owned defers outside PHP bailout boundaries for mandatory backend cleanup,
as the example does for its output buffer. Keep resources needed by PHP alive until
PHP teardown finishes.

## Prepare PHP

Provide a PHP library and matching headers. Target architecture, libc, thread
safety and debug mode must match the PHP build.

For static PHP, [StaticPHP's embed build](https://static-php.dev/en/guide/sapi-reference.html#embed)
produces `libphp.a` on Linux/macOS and `php8embed.lib` on Windows. With a source
checkout of SPC v3:

```sh
php bin/spc build:php bcmath --build-embed
php bin/spc spc-config bcmath --with-packages=php --libs-only-deps
```

Add `--enable-zts` for ZTS. On Windows, run these commands in an MSVC developer
shell. For Linux Docker builds, use SPC's `bin/spc-alpine-docker` wrapper and
export the resulting `buildroot` for use by Zig.

For dynamic PHP on Unix, build PHP with `--enable-embed=shared`. On Windows,
use matching PHP runtime and development packages: the executable links the
`php8.lib` or `php8ts.lib` import library and needs the matching PHP DLLs at runtime.

## Build and run

Run from this directory. For a shared PHP library:

```sh
zig build install run-tests \
  -Dphp-include-dir=/path/to/php/include/php \
  -Dphp-lib-dir=/path/to/php/lib \
  -Dshared=true
./zig-out/bin/custom-sapi hello.php
./zig-out/bin/custom-sapi -r 'echo custom_sapi_greeting(), PHP_EOL;'
```

For a static PHP library, use `-Dshared=false`. Pass each dependency
reported by SPC as `-Dlink-lib=NAME` and each macOS framework as
`-Dlink-framework=NAME`. Use `-Dforce-undefined-symbol=NAME` when a symbol
must be pulled from a static library. These options can be repeated.
For a Linux x86_64 musl PHP build, also pass
`-Dtarget=x86_64-linux-musl`; for Windows, use `-Dtarget=x86_64-windows-msvc`.

Windows builds accept `-Dwindows-zts=true`, `-Dwindows-debug=true` and
`-Dlibc-file=...` when needed. The pinned SPC Windows build also needs PHP's
source directory for its Windows headers; use that directory as
`-Dphp-include-dir`. Place runtime DLLs beside `custom-sapi.exe` for a dynamic
build. See the repository's [SAPI CI script](../../.github/scripts/test-sapi.sh)
for complete platform-specific link arguments.

The requested PHP link mode is strict: it does not fall back to the other mode.
Static PHP does not necessarily mean all system libraries are linked statically.

## Tests and API changes

`zig build run-tests` runs `tests/run.php` with PHP CLI. It starts the custom
SAPI executable for each test script and checks its output and exit status.
PHP CLI must be available as `php`; it does not load the built-in module itself.

After changing the PHP API declarations:

```sh
zig build gen-stub
```

Update the corresponding implementation in `src/main.zig` and rebuild with the
same PHP build options. The SAPI startup passes the module entry as
`additional_module` to register the module.
